# FEICAI Studio 当前架构与下一阶段路线图

本文档用于回答 4 个问题：

1. 当前 `feicai-studio` 已经被重构到了什么程度
2. 现在的代码结构应该如何理解
3. 还剩下哪些真正值得继续投入的技术债
4. 接下来应该优先做哪些产品能力，而不是继续无止境抽象

---

## 1. 当前项目处于什么阶段

`feicai-studio` 已经不再是最初那种“剧本文件驱动的三段式工具”，而是具备完整漫剧工作台雏形的桌面端产品。

当前已经具备的产品骨架：

- 项目可以从 `小说 / 剧情 / 剧本` 3 种入口进入
- 上游输入已经具备编辑入口：
  - `小说原文`
  - `剧情拆解`
  - `剧本`
- 中游工作流已经具备完整阶段模型：
  - `小说`
  - `剧情`
  - `剧本`
  - `剧本审核`
  - `导演`
  - `角色`
  - `服化道`
  - `分镜`
  - `分镜审核`
  - `完成`
- 下游执行上，已经支持：
  - `剧情拆解`
  - `剧本生成`
  - `剧本审核`
  - `导演分析`
  - `角色设计`
  - `服化道`
  - `分镜`
  - `分镜审核`
- `Pipeline` 页面已经不只是看板，而是总控工作台

换句话说：

当前最大的变化，不是“多了几个按钮”，而是这套产品已经从一个零散的 Electron 工具，收成了一个有明确 workflow 模型的生产工作台。

## 2. 当前架构总图

可以把当前项目理解成 6 层。

### 2.1 共享协议层

位置：

- `src/shared/workflow-definition.ts`
- `src/shared/artifact-registry.ts`
- `src/shared/path-resolver.ts`
- `src/shared/types.ts`
- `src/shared/ipc-contracts.ts`
- `src/shared/review-artifacts.ts`

职责：

- 定义阶段
- 定义产物
- 定义目录和路径
- 定义 IPC 输入输出
- 定义审核文件协议

这层现在是整个项目的“事实源头”。
后面如果还要继续扩产品能力，原则上都应该优先在这一层先落协议，再往上接。

### 2.2 主进程工作流层

位置：

- `src/main/workflow/workflow-engine.ts`
- `src/main/engine/state-machine.ts`
- `src/main/engine/state-machine-*`
- `src/main/workflow/workflow-step-runner.ts`

职责：

- 统一执行阶段动作
- 管理自动执行段状态机
- 管理审核与生成动作
- 管理暂停、恢复、重试、跳过

当前这一层已经比早期稳定很多，最大的成果是：

- 不再是两套完全分裂的执行内核
- workflow 和 pipeline 自动段已经共享核心执行能力

### 2.3 主进程数据与文件层

位置：

- `src/main/db/*`
- `src/main/project/*`
- `src/main/services/*`

职责：

- SQLite 索引
- 文件系统扫描
- 项目迁移
- 项目目录检测
- 资产与状态同步

这一层的特点是“双源”：

- 真正产物在项目目录
- 索引和运行态在数据库 / 状态文件

也因此这里仍然是技术债较集中的区域。

### 2.4 Renderer 服务层

位置：

- `src/renderer/services/*`

当前已比较完整的服务分组：

- `project-service`
- `pipeline-service`
- `workflow-actions`
- `pipeline-workflow-service`
- `file-io`
- `file-cache`
- `asset-service`
- `settings-service`
- `export-service`
- `service-contracts`

职责：

- 屏蔽 `window.feicaiAPI`
- 统一返回值契约
- 统一错误文案
- 统一动作调用入口

这一层现在已经基本实现了“页面和 store 不直接碰 preload”的目标。

### 2.5 Renderer hook / 规则层

位置：

- `src/renderer/hooks/*`
- `src/renderer/utils/pipeline-view.ts`
- `src/renderer/utils/pipeline-page-view.ts`
- `src/renderer/utils/pipeline-workflow-summaries.ts`
- `src/renderer/utils/prompt-page-actions.ts`
- `src/renderer/utils/workflow-action-result.ts`

职责：

- 页面级动作编排
- 文档读写状态
- 流程页规则计算
- 摘要统计
- 审核反馈读取

这一层的状态比最开始健康很多，已经不再把大量规则直接堆进页面组件。

### 2.6 Renderer 页面与组件层

关键页面：

- `DashboardPage`
- `ProjectPage`
- `SourceEditorPage`
- `StoryBeatEditorPage`
- `ScriptEditorPage`
- `PromptPage`
- `PipelinePage`
- `ReviewPage`
- `AssetPage`
- `SettingsPage`

关键组件：

- `DocumentWorkflowPage`
- `DocumentEditorToolbar`
- `DocumentEditorShell`
- `WorkflowBoard`
- `WorkflowActionPanel`
- `PipelineControlBar`
- `PrerequisiteGrid`

当前页面层已经明显从“功能全塞一个页面”改成了“页面负责编排，组件负责展示，hook/service 负责逻辑”。

## 3. 已经完成的重构价值

过去 25 轮重构，真正有长期价值的，不是“代码看起来更整齐”，而是下面这些根部变化：

### 3.1 从目录硬编码，收成共享协议

现在阶段、目录、产物、审核文件、配置都已经有统一协议，不再散落硬编码。

这意味着后面继续加能力时，不需要每次全项目找字符串。

### 3.2 从两套执行内核，收成统一 workflow engine

这是整个项目最大的止血点。
如果这个没做，后面每加一个阶段都会指数级变乱。

### 3.3 从页面直连 IPC，收成 service 层

这意味着：

- 页面逻辑更轻
- 测试更容易补
- 后面要改 preload / IPC 契约，不需要全页面改

### 3.4 从页面各写一套编辑器逻辑，收成统一文档模型

现在 `Source / Story / Script / Prompt` 已经具备统一的文档读写和页面骨架。

这对后续继续加“导演分析编辑页”“角色资产页”“故事 bible 页”很关键。

### 3.5 从没有测试保护，到已有核心基线

现在至少这些层已经开始有测试：

- 输出解析
- 审核协议
- 工作流状态推导
- 流程页纯规则
- service bridge
- action helper

这意味着后面改产品逻辑，不再只能靠手工点页面回归。

## 4. 还剩的核心技术债

下面这些是“值得继续做”的技术债，不是机械性洁癖。

### 4.1 仍然没有真正统一的项目级故事资产层

现在已有：

- `source/novel.md`
- `story/episode-beats/epXX.md`
- `script/epXX.md`

但还缺：

- `season bible`
- `人物关系总表`
- `世界观约束`
- `角色弧线`
- `章节到集的映射`

这会直接影响跨集一致性。
如果要做成真正的漫剧工作台，这个是下一阶段最该补的“产品级基础设施”。

### 4.2 审核仍然偏弱，缺少明确的业务闭环

虽然现在有：

- 剧本审核
- 分镜审核
- 审核文件落盘

但还缺：

- 审核维度结构化
- “不通过 -> 修改建议 -> 回填编辑页”的更强闭环
- 审核历史对比
- 人工审核确认态

目前更像“AI 给意见”，还不够像“生产流程里的质量闸门”。

### 4.3 工作流状态与业务状态仍有简化

现在很多阶段状态本质上还是：

- 文件存在
- 审核文件存在
- 产物存在

这比最早已经好很多，但仍然不够细。

未来更合理的状态还应该区分：

- `draft`
- `generated`
- `review_failed`
- `approved`
- `needs_revision`
- `locked`

否则 workflow 会越来越难表达真实制作状态。

### 4.4 资产层仍偏薄

当前角色设计和资产管理已经起步，但离真正的“资产库”还有距离。

缺的不是页面，而是资产模型：

- 角色版本
- 角色变体
- 服装阶段
- 道具与场景关联
- 分镜 prompt 对资产引用的可追踪性

### 4.5 `PipelinePage` 仍然是产品中心，但还不是统一工作台

现在它已经是总控台，但仍偏“单集执行工作台”。
未来如果要继续升级，应该补：

- 全季视角
- 阶段批处理
- 质量总览
- 待修项聚合
- 审核 backlog

## 5. 现在不该继续优先做的事

为了避免掉进“无止境重构”，下面这些我建议先降优先级。

### 5.1 不要继续优先做纯页面抽象

像：

- 再抽一层 editor layout
- 再抽一层 card wrapper
- 再抽一层 page shell

这些现在的收益已经明显下降了。
除非业务新增导致重复再次爆发，否则先不要继续抽。

### 5.2 不要继续优先做更细的 service helper 美化

现在 service 层已经够用了。
继续做更细的 helper 风格统一，边际收益不高。

### 5.3 不要继续优先做“为了状态机而状态机”的抽象

核心 workflow 已经能撑业务。
除非产品要引入新的真实状态，否则不建议继续为了理论完整性再重构状态模型。

---

## 6. 接下来最值得做的产品能力

这里不是“技术任务列表”，而是“产品投入优先级”。

### P0：故事资产层补齐

优先级最高。

目标：

- 增加 `season bible`
- 增加角色关系与世界观约束
- 让剧情拆解和剧本生成不再只吃小说原文

原因：

如果这层不补，后面的角色、服化道、分镜都会越来越像单集临时生成，而不是全剧生产。

### P0：审核闭环增强

目标：

- 剧本审核问题结构化
- 分镜审核问题结构化
- 审核问题自动回流到编辑页
- 增加人工确认 / 驳回 / 通过态

原因：

对于工作台产品，审核不是附属功能，而是生产线核心。

### P1：资产库升级

目标：

- 角色资产版本化
- 角色 / 场景 / 道具引用统一
- 让 prompt 能真正引用稳定资产，而不是只拼文本标签

原因：

这会直接影响视觉一致性和后续出图质量。

### P1：Pipeline 升级为全局制作台

目标：

- 单集视角 + 全季视角切换
- 阶段批量执行
- 卡点统计
- 审核未通过聚合
- 产物质量摘要聚合

原因：

现在 `Pipeline` 更像一集的操作台，下一步要变成制片工作台。

### P2：导出与交付能力

目标：

- 导出审核通过版本
- 导出资产包
- 导出制作包
- 导出分镜 prompt 包

原因：

这会决定它到底是“内部工具”还是“生产交付工具”。

## 7. 建议的下一阶段实施顺序

如果按 4 到 6 周一个中短期阶段来看，我建议这样排。

### 阶段 A：停止纯重构，补故事层

目标：

- 增加 `season bible`
- 增加故事总表编辑入口
- 剧情拆解接入故事 bible

这是最重要的一步。

### 阶段 B：补审核闭环

目标：

- 审核结构化
- 审核历史与版本对比
- 人工确认态
- 失败回流编辑页

这一步决定工作台是否真的可用于制作。

### 阶段 C：升级资产层

目标：

- 角色资产库正式化
- 场景资产库正式化
- prompt 引用资产追踪

### 阶段 D：升级 Pipeline 为全局工作台

目标：

- 从单集总控，升级为项目/季总控

---

## 8. 一个明确的判断

现在 `feicai-studio` 已经到了一个很关键的分界点：

继续纯重构，收益会快速下降。
继续补业务闭环，收益会开始明显上升。

也就是说，从这一刻起，更应该把它当成“要做成的产品”来推进，而不是“还没整理好的代码库”。

---

## 9. 我对下一步的直接建议

如果立刻进入下一轮，我建议不要做第 26 段“再抽象一层”，而是直接开始做这 3 件事中的第 1 件：

1. 增加 `season bible / 世界观 / 角色关系` 的项目级故事层
2. 增加剧本审核与分镜审核的结构化回流页
3. 升级角色资产库和资产引用模型

如果只能选一个，我建议先做第 1 个。

因为它会决定后面所有中下游生成质量的上限。
