# FEICAI Studio 制作工作台 UI/UX 简化与一致性优化方案

> **性质**：基于当前源码的审计与可执行设计方案，不是 UI 已完成声明。本文只新增文档，不改变生产代码、配置、模型、真实项目或 userData。
>
> **审计边界**：本次阅读了 renderer 页面、布局/编辑器/流水线组件、相关服务与已有设计文档；没有启动 Electron、生产 API、真实模型或真实项目交互。因此“代码确定”来自静态源码，“待验证”必须由隔离 DOM/人工走查确认。
>
> **基线声明**：近期已合入的“小说首次草稿→审核→剧情库存→对应集”和总控/矩阵/批处理简化视为已修项。本文不把它们列成待修功能，只评估其余入口是否形成一致主线。图片/视频合同或设置项不等于生产链已接通。

## 1. 结论摘要与优先级

最严重的不是缺少页面，而是同一件事有多套入口和身份上下文：侧栏把“流水线、批量执行、原文、剧情、剧本、素材库、提示词、审核报告、项目体检、导出”全部平铺；项目页又有矩阵、流水线按钮、剧情库存/章节扫描；编辑页还同时提供工具栏和工作流侧栏动作。用户容易在“项目层、当前集、后台任务”之间迷失。

推荐只建立一条默认主线：**项目总览 → 选择本集 → 内容（原文/剧情/剧本）→ 审核通过 → 后续制作 → 运行任务/失败反馈**。矩阵和批处理是项目层的按需能力；设置、体检、导入导出保留在项目管理；恢复、审核反馈、当前错误和失败诊断在当前上下文显式可达，不能一律藏进高级。全局制作并发仍为 1。

P0 先做身份和反馈可靠性，再做共用导航、状态和动作规则；P1 收敛编辑/审核/总控的页面职责；P2 只在真实媒体链已验收后开放媒体工作台，不提前把图片/视频入口伪装成可生产能力。

**路径中的阻塞/负担**：

1. 首次用户不应先理解“流水线、批量执行、提示词、素材库”的边界；这些应从项目总览的下一步或“更多”进入。
2. “项目页矩阵”和“制作总控”都能表达下一步，但没有明确谁是默认工作入口。推荐项目页是默认首页，总控改名为“本集制作”并只服务当前集。
3. 编辑页的工作流侧栏是强主线；工具栏只保留文件级动作。重复的“前往流程页”应合并为一个上下文动作。
4. 批处理不得成为首次制作入口。它应先展示预检：将执行、跳过、阻塞、可能计费；失败项进入任务详情，而不是只看日志。

## 4. 推荐信息架构（唯一推荐）

### 4.1 三层身份

- **项目层**：项目总览、分集矩阵、待处理、批量预检、项目管理。所有卡片显示项目名称；不把另一个项目的后台运行当成本项目进度。
- **集层**：本集制作，固定显示“项目 / 第 N 集 / 当前入口 / 当前产物版本”。内容编辑、审核反馈、后续制作都从这里进入。
- **运行层**：任务中心/运行详情，显示任务所属项目、集、阶段、输入版本、输出位置、状态、失败原因和恢复动作；切换页面不取消任务。

全局只允许一个制作任务执行。当前浏览项目与后台运行项目并列显示；后台任务卡提供“查看运行任务”，不提供隐式切换当前项目。

### 4.2 导航与返回

```text
项目总览（默认首页）
├─ 当前待办 / 继续上次工作
├─ 分集制作矩阵
├─ 批量预检（高级）
├─ 本集制作（当前集）
│  ├─ 内容：原文 / 剧情 / 剧本
│  ├─ 审核与反馈
│  └─ 后续制作：导演 / 服化道 / 分镜（当前实际产物范围）
├─ 任务中心（跨页面运行、失败、恢复）
└─ 项目管理（设置 / 体检 / 备份恢复 / 导入导出 / 诊断）
```

旧路由继续兼容并重定向到上述上下文，不通过删除路由制造不可达；`novel/story/script` 三入口保留为内容入口或项目创建入口。默认首页为项目总览；编辑/本集制作返回项目总览并保留 `projectId`、`ep` 和选中对象，任务中心返回原来源页面。

### 4.3 主动作规则

每页只允许一个视觉主动作，最多两个次级动作：

1. 缺输入：主动作“补齐输入”，说明缺什么并直达位置。
2. 草稿未保存：主动作“保存”；生成/审核禁用并说明“先保存”，不静默覆盖。
3. 已保存未审核：主动作“提交审核”。
4. 审核未通过：主动作“查看问题并修改”；次级“重新审核”。不显示“进入下游”为可用动作。
5. 审核通过：主动作“进入下一步”；次级“查看审核反馈/版本”。
6. 执行中：主动作区域变为状态和“查看任务”；停止是危险次级动作，需确认并等待结算。
7. 失败：主动作“查看失败原因”；仅在可安全重试时显示“重试”，不把未知结果当失败或成功。
8. 已中断：主动作“恢复任务”；另提供“按当前配置重新开始”，明确这是新执行。
9. 高级动作（导入、导出、日志、复制、重载）不与主动作争夺视觉层级。

```text
│ 分集制作矩阵             [全部/待处理] [刷新]                    │
│ 集  剧情       剧本       导演       服化道     分镜              │
│ 01  已通过     执行中     未开始     未开始     未开始            │
│ 02  待修改     未开始     已锁定     未开始     未开始            │
│       点击单元格进入“本集制作”，不在矩阵内编辑正文              │
├──────────────────────────────────────────────────────────────┤

```

宽屏矩阵可横向滚动但首列冻结；窄屏改为“集卡片 + 阶段横向滚动”，不压缩成不可读小格。空项目显示创建/导入；加载显示旧快照且注明“暂不提供下一步”；失败显示原因和刷新/进入诊断；无集数引导到项目设置规划集数。线框中“打开本集制作”是该页唯一主动作；待办文字只解释原因，不另设“处理待办”按钮，批量预检和查看运行任务是有明确标签的次级/上下文动作。

### 5.2 内容编辑与审核（集层）

```text
┌ 项目A / 第02集 / 剧情                         [返回项目] [集选择] ┐
│ 状态：草稿已保存 · 审核未通过 · 当前稿（版本标识待版本服务）      │
├ 来源/上下文 ───────┬ 正文编辑区 ─────────────┬ 当前问题与动作 ─────┤
│ 原文章节            │ Markdown/正文           │ 严重 1 · 主要 2      │
│ 绑定剧情点          │                         │ [定位问题]           │
│ 前后集衔接          │                         │ 修改后需重新审核     │
│ 人物/场景（只读）   │                         │ [保存并提交审核]     │
│                     │                         │ [保存] [导入]        │
└─────────────────────┴────────────────────────┴────────────────────┘
```

右侧审核问题点击定位正文；问题分新出现、仍存在、已解决、复发。恢复通知位于正文上方且不被侧栏遮挡。草稿冲突使用明确对话框“恢复本地草稿 / 重新载入磁盘 / 覆盖磁盘（需确认）”；不使用 toast 代替关键选择。窄屏正文优先，来源/问题变为带标题的抽屉；主动作固定在底部操作栏，焦点顺序为标题→状态→正文→主动作→次级动作→抽屉。

### 5.3 运行状态/失败反馈（运行层）

```text
┌ 运行任务 ─ 项目A / 第02集 / 剧本审核                         [返回来源] ┐
│ 状态：失败（审核结果无效）  开始 10:32  结果：未提交采用稿             │
├ 输入摘要：当前剧本稿 · 当前有效剧情审核 · 本次生效设置（设计目标）   │
├ 步骤：保存输入 → 调用 → 解析 → 审核 → 提交                          │
│        ✓             ✓       ✕                                      │
├ 发生了什么：输出缺少必需段落，未改变已有有效稿                         │
│ [查看审核反馈] [修改输入] [安全重试] [查看详细记录]                    │
└─────────────────────────────────────────────────────────────────────┘
```

显示“未知结果”时只允许执行当前已有的状态查询/刷新或进入诊断；除非任务服务明确提供恢复动作，否则不显示“恢复”，也不显示再次生成。显示暂停处理中/停止处理中时禁用冲突启动。日志详情折叠在步骤之后，用户文案不暴露 provider 合同、`operationId` 等实现字段；技术详情可在“复制诊断信息”中脱敏导出。安全重试只在现有服务能证明可安全重试时出现，否则显示“查看原因”，不能由 UI 推断幂等。

## 6. 设计目标与当前实现边界

线框里的“当前稿/版本标识待版本服务”、输入摘要、问题定位、问题生命周期、任务详情步骤、候选采用、安全重试均是目标交互，不是本仓库当前已经持久化或可调用的 API。当前代码已能支持的基础是：Markdown 草稿保存/恢复与冲突选择、最近审核结果展示、队列/流水线状态、失败计数与日志、项目/集上下文。以下能力必须先补相应服务或数据合同，再进入 UI：

- **版本与输入快照**：需要版本/引用合同和持久化任务快照；P0 不得只改 renderer 就声称已有 `v3`、`v2` 或可复现快照。
- **问题定位与生命周期**：需要审核问题稳定 code、对象版本、段落锚点和处理记录；当前审核反馈可展示，但“点击定位正文”“新出现/仍存在/复发”是后续目标。
- **任务详情与安全重试**：需要持久任务/请求尝试、幂等或未知结果判断和恢复服务；当前 UI 只能展示现有队列/流水线状态、失败信息、日志和实际支持的停止/暂停动作。
- **候选/采用**：需要候选、采用记录和媒体引用；当前素材页的角色/场景提示词编辑不等于已有候选采用流程。

因此 P0 的立即交付只能是基于现有数据的身份过滤、错误上下文和恢复通知文案；P1/P2 的版本、定位、任务恢复、安全重试与采用流程必须在依赖完成后分别验收，不能把目标线框当作当前功能清单。

## 7. 统一组件、文案和可达性规范

### 6.1 共用组件边界

| 组件                   | 责任                                 | 不负责                    |
| ---------------------- | ------------------------------------ | ------------------------- |
| `ProjectContextHeader` | 项目、入口、当前集、版本、返回       | 不显示或修改任务内部 ID   |
| `EpisodeStageNav`      | 当前集阶段和可达性                   | 不自行决定审核门禁        |
| `NextActionCard`       | 一个主动作、原因、阻塞入口           | 不复制完整流程图          |
| `StatusBadge`          | 统一状态词、图标/文字、可读说明      | 不用颜色单独表达状态      |
| `ReviewIssuePanel`     | 问题定位、反馈、处理状态             | 不把“已处理”自动改成 PASS |
| `TaskStatusCard`       | 项目/集/阶段身份、状态、控制         | 不以日志代替状态机        |
| `RecoveryNotice`       | 恢复、冲突、失败和选择               | 不自动覆盖正文            |

优先抽共用组件和 view-model，再调整页面；不新建第二套总控或第二套状态机。状态数据仍由现有 stores/主进程合同提供，UI 不自行授予审核或采用资格。

### 6.2 状态词和反馈

统一使用：`未开始`、`缺少输入`、`草稿未保存`、`待审核`、`审核未通过`、`已通过`、`已采用`、`需要更新`、`执行中`、`暂停处理中`、`已暂停`、`停止处理中`、`已中断`、`结果未知`、`失败`、`已完成`。作品状态（产物/审核/采用）与任务状态（运行/暂停/失败）分两行显示。

成功/警告/失败/加载分别使用页面内 `status/alert` 和 toast：关键失败必须持久可见；加载不清空旧的有效快照；空状态给出原因和下一动作；禁用按钮旁边写原因；没有“请求成功”就不能显示已完成。费用和能力未知显示“未知”，不显示零或虚假百分比。

### 6.3 键盘、焦点和窄屏

- 所有图标按钮有可读 `aria-label` 或可见文字；焦点环不可隐藏，Tab 顺序遵循页面阅读顺序。
- 可展开审核项、矩阵横向滚动区、弹窗关闭和恢复选择均支持键盘；弹窗打开时焦点进入弹窗，关闭后回到触发按钮，Escape 关闭非破坏性弹窗。
- 不以颜色/emoji 作为唯一状态信息；状态徽标同时显示文字，严重度使用文字和图标。
- 宽屏：项目页两层信息（建议 + 矩阵）；编辑页来源/正文/问题三栏，最小正文宽度优先。
- 窄屏：正文优先、来源和问题抽屉化；底部固定主动作不遮挡输入；矩阵改卡片/阶段横滑，禁止页面级横溢；批量列表分页或虚拟化。

```bash
        continue
    if Path(target).name in {'foundation-capabilities-design.md', 'production-workbench-media-plan.md'}:
        fallback_file = fallback / Path(target).name
        assert fallback_file.exists(), fallback_file
    else:
        raise SystemExit(f'missing local reference: {target}')
print('run_checks: document structure and references OK')
PY
cat >/tmp/feicai-ui-ux-check.mk <<'MAKE'
.PHONY: run_checks
ROOT ?= $(CURDIR)
run_checks:
	ROOT="$(ROOT)" python3 /tmp/feicai-ui-ux-check.py
	git -C "$(ROOT)" diff --check -- feicai-studio/docs/ui-ux-optimization-plan.md
MAKE
# 从仓库根执行；worktree 缺少的两份设计文档会自动从 git common dir 的主工作区读取
make -f /tmp/feicai-ui-ux-check.mk run_checks
```
