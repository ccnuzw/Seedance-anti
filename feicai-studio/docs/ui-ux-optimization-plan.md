# FEICAI Studio 制作工作台 UI/UX 简化与一致性优化方案

> **性质**：基于当前源码的审计与可执行设计方案，不是 UI 已完成声明。本文只新增文档，不改变生产代码、配置、模型、真实项目或 userData。
>
> **审计边界**：本次阅读了 renderer 页面、布局/编辑器/流水线组件、相关服务与已有设计文档；没有启动 Electron、生产 API、真实模型或真实项目交互。因此“代码确定”来自静态源码，“待验证”必须由隔离 DOM/人工走查确认。
>
> **基线声明**：近期已合入的“小说首次草稿→审核→剧情库存→对应集”和总控/矩阵/批处理简化视为已修项。本文不把它们列成待修功能，只评估其余入口是否形成一致主线。图片/视频合同或设置项不等于生产链已接通。

## 1. 结论摘要与优先级

最严重的不是缺少页面，而是同一件事有多套入口和身份上下文：侧栏把“流水线、批量执行、原文、剧情、剧本、素材库、提示词、审核报告、项目体检、导出”全部平铺；项目页又有矩阵、流水线按钮、剧情库存/章节扫描；编辑页还同时提供工具栏和工作流侧栏动作。用户容易在“项目层、当前集、后台任务”之间迷失。

推荐只建立一条默认主线：**项目总览 → 选择本集 → 内容（原文/剧情/剧本）→ 审核通过 → 后续制作 → 运行任务/失败反馈**。矩阵和批处理是项目层的按需能力；设置、体检、导入导出保留在项目管理；恢复、审核反馈、当前错误和失败诊断在当前上下文显式可达，不能一律藏进高级。全局制作并发仍为 1。

P0 先做身份和反馈可靠性，再做共用导航、状态和动作规则；P1 收敛编辑/审核/总控的页面职责；P2 只在真实媒体链已验收后开放媒体工作台，不提前把图片/视频入口伪装成可生产能力。

**路径中的阻塞/负担**：

1. 首次用户不应先理解“流水线、批量执行、提示词、素材库”的边界；这些应从项目总览的下一步或“更多”进入。
2. “项目页矩阵”和“制作总控”都能表达下一步，但没有明确谁是默认工作入口。推荐项目页是默认首页，总控改名为“本集制作”并只服务当前集。
3. 编辑页的工作流侧栏是强主线；工具栏只保留文件级动作。重复的“前往流程页”应合并为一个上下文动作。
4. 批处理不得成为首次制作入口。它应先展示预检：将执行、跳过、阻塞、可能计费；失败项进入任务详情，而不是只看日志。

## 4. 推荐信息架构（唯一推荐）

### 4.1 三层身份

- **项目层**：项目总览、分集矩阵、待处理、批量预检、项目管理。所有卡片显示项目名称；不把另一个项目的后台运行当成本项目进度。
- **集层**：本集制作，固定显示“项目 / 第 N 集 / 当前入口 / 当前产物版本”。内容编辑、审核反馈、后续制作都从这里进入。
- **运行层**：任务中心/运行详情，显示任务所属项目、集、阶段、输入版本、输出位置、状态、失败原因和恢复动作；切换页面不取消任务。

全局只允许一个制作任务执行。当前浏览项目与后台运行项目并列显示；后台任务卡提供“查看运行任务”，不提供隐式切换当前项目。全局运行条与任务中心的具体位置、状态映射和交互见 [第 6 节“全局任务状态与进度中心”](#6-全局任务状态与进度中心)。

### 4.2 导航与返回

```text
项目总览（默认首页）
├─ 当前待办 / 继续上次工作
├─ 分集制作矩阵
├─ 批量预检（高级）
├─ 本集制作（当前集）
│  ├─ 内容：原文 / 剧情 / 剧本
│  ├─ 审核与反馈
│  └─ 后续制作：导演 / 服化道 / 分镜（当前实际产物范围）
├─ 任务中心（跨页面运行、失败、恢复）
└─ 项目管理（设置 / 体检 / 备份恢复 / 导入导出 / 诊断）
```

旧路由继续兼容并重定向到上述上下文，不通过删除路由制造不可达；`novel/story/script` 三入口保留为内容入口或项目创建入口。默认首页为项目总览；编辑/本集制作返回项目总览并保留 `projectId`、`ep` 和选中对象，任务中心返回原来源页面。

### 4.3 主动作规则

每页只允许一个视觉主动作，最多两个次级动作：

1. 缺输入：主动作“补齐输入”，说明缺什么并直达位置。
2. 草稿未保存：主动作“保存”；生成/审核禁用并说明“先保存”，不静默覆盖。
3. 已保存未审核：主动作“提交审核”。
4. 审核未通过：主动作“查看问题并修改”；次级“重新审核”。不显示“进入下游”为可用动作。
5. 审核通过：主动作“进入下一步”；次级“查看审核反馈/版本”。
6. 执行中：主动作区域变为状态和“查看任务”；停止是危险次级动作，需确认并等待结算。
7. 失败：主动作“查看失败原因”；仅在可安全重试时显示“重试”，不把未知结果当失败或成功。
8. 已中断：主动作“恢复任务”；另提供“按当前配置重新开始”，明确这是新执行。
9. 高级动作（导入、导出、日志、复制、重载）不与主动作争夺视觉层级。

### 6.2 运行条显示合同与进度规则

运行条只展示**当前真实活跃任务**：项目、集/批次、当前阶段、归一化状态，以及服务有依据的步骤进度。它不显示“看起来像进度”的计时百分比、LLM 流长度百分比、项目完成百分比或 `breakdownProgressPct` 代替运行进度。

- **pipeline**：阶段集合必须由启动模式确定。全流程可以显示“已完成阶段/3”（导演、服化道、分镜）；单阶段显示“已完成阶段/1”。若当前状态只说明正在某阶段而没有阶段完成事件，则只显示“当前阶段：导演分析中”，不计算百分比。
- **独立 workflow**：一次动作（剧情生成、剧情审核、剧本生成、剧本审核、角色设计、分镜审核）最多显示“步骤 0/1”或“1/1”；开始、成功/失败必须来自任务快照/结果，不以 IPC promise 发出就显示完成。当前 workflow snapshot 没有统一结果写入字段，故“已写入结果”必须等服务合同补齐后显示。
- **batch queue**：运行条显示队列当前真正运行的 episode task 和其 `progress`/当前子步骤；可以另显示“队列遍历 2/8”，但必须标为队列进度，不能当作当前任务成功。`pending` 只表示排队，不能显示为运行中。队列只给出服务实际记录的 `tasks`、`steps`、`cursor`，不得按耗时或集数猜测子步骤总数。
- 没有总步骤、阶段完成事件或可验证收据时，进度字段隐藏，保留状态和阶段。进度退化到“未知”是正确行为；禁止补一个 37% 或“即将完成”。

全局只允许一个活跃制作租约。`ExecutionLease` 当前以模块级 `active` 拦截 pipeline、workflow、batch 及数据维护；设计保持这一互斥，不用 renderer 禁用按钮代替主进程准入。暂停持有租约，停止须等待在途调用和文件提交结算后再释放；运行条在“停止请求已接受”后显示 `stopping`，不能立即改成已停止。

### 6.3 任务中心分组、身份和状态映射

任务中心固定分为三组，顺序不因当前路由或当前项目改变：

1. **活跃**：`queued/pending`、`running`、`paused`、`stopping`、`interrupted` 中仍需用户确认或可继续处理的任务。容量为 1 时最多一个真正活跃制作任务；恢复态仍需把任务身份和项目显示清楚。
2. **待确认结果**：停止、窗口关闭、重启、事件缺失或提交恢复未完成后无法证明最终结果的任务。显示“结果待核实”，不能自动归入失败或成功；只能刷新、检查提交/诊断或结束任务。
3. **最近结果**：已确认的 `failed`、`succeeded/complete`（以及用户已确认结束的 stopped/interrupted）。只保留服务合同规定的历史数量；当前代码的 pipeline task 列表只保留最新一个，不得把它描述为完整历史。

统一状态词和映射如下。括号内是当前代码证据，不代表所有映射都已实现：

| 统一状态 | 用户文案 | 当前来源与归一化规则 | 允许的下一步 |
| --- | --- | --- | --- |
| `queued/pending` | 排队中 | batch task `pending`；pipeline/workflow 当前没有排队快照，直接启动前不得伪造 queued | 查看详情、停止（仅服务提供时） |
| `running` | 运行中 | pipeline/workflow task snapshot `running`；batch queue/task `running` | 查看、暂停/停止（按任务类型实际支持） |
| `paused` | 已暂停 | execution lease 暂停或 pipeline snapshot `paused`；batch queue `paused` | 恢复、停止（按服务提供） |
| `stopping` | 停止处理中 | batch queue `stopping`，或统一任务服务已接受停止但尚未结算 | 只查看；禁用冲突启动，等待最终结果 |
| `interrupted` | 已中断，结果待核实 | batch queue 重启时将运行/暂停/停止态改为 `interrupted`；其他任务若失去进程状态也进入待核实 | 刷新、诊断、明确恢复/结束（仅服务提供时） |
| `failed` | 失败 | pipeline snapshot `failed`、batch task `error` 或 workflow result `success:false`；必须带阶段和原因摘要 | 查看原因；仅合同证明安全时重试 |
| `succeeded/complete` | 已完成 | pipeline snapshot `completed` 且结果/提交已确认；workflow `success:true` 且输出/审核结果已确认；batch task `done` | 查看结果、进入下一步 |
| `unknown` | 未知结果 | 快照缺失、身份不匹配、事件乱序造成缺口、窗口/应用关闭后没有最终收据 | 只刷新、检查提交、进入诊断；禁止推测成功、失败或安全重试 |

`complete` 不是队列遍历完成的同义词。batch `BatchQueueState.status=completed` 只表示 cursor 遍历结束；同一队列中的 task 仍可能是 `error` 或 `skipped`。任务中心必须同时显示“队列已遍历完成”和“本任务失败/跳过”，并以任务自身成功结果决定“成功”。pipeline 的 `episode_complete`/阶段完成、workflow 的 `WorkflowStepRunResult.success` 与 batch task 的 `done` 也要分别映射，不能把一条日志或 IPC 返回成功当作所有层级成功。

每个控制请求都携带并核验 `projectId + taskId + runId`（批队列至少还要有 queueId、episode 和当前 operation 身份），必要时显示集/阶段供用户确认。当前项目切换只改变页面过滤/回退导航，绝不能覆盖任务控制目标。旧的无目标 IPC 只允许在容量 1 的兼容期映射唯一活动任务；任务中心新入口必须使用定向控制。

### 6.4 任务类型与控制矩阵

任务详情用“来源”区分单步 workflow、pipeline 和 batch queue，不把三者拼成一个虚假的阶段链：

| 来源 | 当前可观察身份/状态 | 任务中心展示的步骤 | 仅展示服务实际支持的控制 |
| --- | --- | --- | --- |
| 独立 workflow | `PipelineTaskSnapshot.kind=workflow`，含 project/episode/stage/taskId/runId；当前快照为进程内 | 该 action 的 1 步；结果来自 workflow result/输出或审核收据 | 当前服务能定向暂停/恢复/停止时显示；重试、跳过必须等 workflow 合同提供，不能复用 pipeline 的重试 |
| pipeline | `kind=pipeline`、pipeline context、stage 状态和 task identity | 单阶段 1 步或全流程 3 阶段；只按阶段事件/状态计数 | 当前 IPC 支持 pause/resume/abort/retry/skip，但按当前 stage、状态和任务 identity 判定；停止显示结算中 |
| batch queue | `batch-queue.json` 的 queue id、projectId、mode、cursor、tasks、steps、inFlight/operationId | queue 遍历进度 + 当前 episode task 子步骤，分开显示 | pause/resume/stop；恢复仅限 interrupted/stopped 且主进程允许；批量失败没有现成安全重试按钮 |

“暂停”与“停止”均需确认对话框，确认文案包括项目、集、阶段和状态；不要因为用户当前打开了项目 B 就把项目 A 的控制请求改成 B。`operationId`、`runId` 等技术身份默认折叠到“诊断信息”，但控制协议仍必须在主进程核验，不能仅依赖显示层。

### 6.5 成功/失败 sticky 通知与详情

任务进入确认的 `failed` 或 `succeeded/complete` 时，在应用壳层产生持久通知；它不使用现有 4 秒自动消失的普通 toast 语义。用户离开模块、切换项目或关闭任务 drawer 后，通知仍留在“待确认结果/最近结果”和顶栏结果入口，直到用户明确查看/确认。相同 `taskId + runId + terminal revision` 的重复事件不得重复堆叠通知。

通知至少包含：

- 项目、集/批次、任务来源和失败/成功阶段；
- 原因摘要（失败）或结果摘要（成功）；
- “结果是否写入”：`已确认写入`、`未写入/保留原稿`、`待核实`，没有证据就显示待核实；
- 一个可执行的下一步导航，例如进入对应审核反馈、打开产物、查看批队列或进入诊断；导航带原任务身份，不切换为当前项目的同名集；
- “查看详细记录”折叠日志、提交收据和脱敏诊断信息，不把日志当作状态本身。

未知结果通知只显示“结果待核实”，操作限于刷新、检查本地提交/恢复记录和诊断；不显示“再次生成”“恢复成功”“安全重试”。失败通知也只有在服务提供幂等/收据证明时才显示重试，否则主动作是“查看失败原因”。成功通知不得只依据 `queue.status=completed`，必须引用对应 task/result 的可验证完成证据。

### 6.6 已实现能力、缺口与持久化边界

| 代码事实 | 当前可支撑的设计 | 仍缺少的服务合同/明确边界 |
| --- | --- | --- |
| `AppShell` 只包住 `Header` 与 `Outlet`；`Header` 当前显示 pipeline store 的运行/完成/错误标签 | 可把全局运行条放在应用壳层，切路由不依赖页面 mount | 尚无统一任务 view-model、任务中心路由/drawer、batch/workflow/pipeline 合并快照 |
| `pipelineStore` 有 `context`、`runIdentity`、事件监听和按 project/run 过滤；`pipeline-task` 有 taskId/runId/projectId、kind、状态和定向 IPC | 可显示 pipeline 的真实 identity、阶段和部分状态；迟到事件可按身份丢弃 | task snapshot 由 `pipeline-service` 模块变量 `currentTask` 保存，只保留最新任务，未形成持久历史、revision/seq 或重启恢复合同 |
| 独立 workflow 创建同样的 task snapshot，并共用 execution lease/task sink | 可将独立 workflow 纳入任务中心，明确显示为单步 workflow | 当前 snapshot 没有统一总步骤、resultWritten、失败分类、持久 task record；不能宣称 workflow 重启可恢复 |
| batch queue 用 `userData/batch-queue.json` 原子写入 queue state，包含 cursor、tasks、steps、inFlight/operationId；初始化时运行态转 `interrupted` | 可在本进程和重启后展示一个批队列快照，区分队列遍历与每个 task 结果；已提交子步骤可按收据恢复 | 这是单队列 JSON，不是统一 SQLite 任务表或完整历史；pipeline/workflow 没有同等级持久化。窗口/应用关闭或 IPC 断开后的外部结果仍可能未知，必须先显示结果待核实 |
| `ExecutionLease` 是全局单一 active，暂停持有租约，停止等待 settled；runtime 向所有窗口广播事件 | 可保持全局互斥、多窗口状态广播和停止中的视觉语义 | 缺少统一事件 `seq/revision`、快照水位、结果通知确认和批队列/独立 workflow 的同形控制合同 |
| pipeline 状态有阶段和日志，batch task 有 `progress`、steps、error；项目状态/提交恢复有 operationId 校验 | 可显示阶段、原因摘要、已验证提交和有限的步骤数 | 当前没有跨任务统一的 `completedSteps/totalSteps/resultWritten` 字段；不能从 elapsed、日志行数、文件存在或 queue completed 推断百分比/成功 |

因此，**不宣称已经持久化**：当前只能说 batch queue 有文件持久化快照，pipeline/workflow 任务 identity/snapshot 主要在主进程内存中；没有统一任务历史。应用重启后，batch 运行态会被代码标为 `interrupted`，而其他任务可能只剩产物/提交痕迹或完全没有快照，UI 一律先进入“结果待核实”，再依据精确 `operationId`、提交收据和项目身份诊断。未来若增加 SQLite `tasks/task_steps`，仍需保留 `projectId`、`taskId`、`runId`、`operationId` 隔离，且恢复获得新 runId，不把旧事件当作新运行。

### 6.8 状态矩阵验收

以下矩阵是实施验收入口；每格都要用真实主进程/受控 provider 事件验证，不用静态 mock 的“看起来正确”替代。所有场景都必须保持全局并发为 1。

| 场景 | 触发与观察 | 必须看到的结果 | 禁止行为 |
| --- | --- | --- | --- |
| 运行中切换模块 | 项目 A 的 pipeline/workflow/batch 运行时切 Sidebar 到项目页、审核、设置 | 顶栏仍显示 A/集/阶段/真实状态；任务中心可回详情，页面 B 不覆盖任务身份 | 切页清空、显示 B 的项目/集、自动取消任务 |
| 独立 workflow | 直接触发剧情/剧本生成或审核，观察 task `kind=workflow` | 以单步 workflow 展示 0/1 或 1/1，成功/失败以 result/提交确认；控制按实际合同出现 | 把 workflow 显示成三阶段 pipeline、借用 pipeline retry |
| 批量某任务失败但队列遍历结束 | batch 中一个 task 返回 error，后续 task 完成或 skipped，queue status 变 completed | “队列已遍历完成”与失败 task 分开；失败通知 sticky，说明阶段/原因/写入情况 | 仅显示“批量成功”、把 completed 当所有 task succeeded |
| 停止中 | 对运行任务确认停止，模拟在途 provider/文件提交尚未结算 | 显示 stopping；控制禁用；结算后才 stopped/failed/unknown 并释放全局租约 | 立即显示已停止、立即允许第二个制作任务 |
| 窗口关闭/应用重启未知 | 运行时关闭窗口/重启，在结果收据不可证明时重新打开 | pipeline/workflow 无快照或 batch interrupted 均进入结果待核实；可刷新/诊断；batch 仅按精确收据恢复 | 推测成功、自动安全重试、宣称所有任务已持久化 |
| 切换当前项目 | 任务属于 A，当前项目切到 B，再从任务中心暂停/停止 | 控制仍定向 A；确认对话框显示 A 的项目/集/阶段；B 的页面不会改写参数 | 以当前项目 B 覆盖 target，或误显示 B 的状态 |
| 多个事件乱序 | 先送旧 run/旧 revision 的完成或错误，再送新 run 的 running/terminal | 按 taskId/runId/revision/seq 丢弃旧事件，必要时重取快照；sticky 不重复 | 用 updatedAt/到达顺序覆盖新状态，重复通知 |
| 完成结果 sticky | 任务完成后离开来源模块、关闭 drawer、切换项目 | 成功通知保留到明确查看/确认，含阶段、结果写入和下一步导航；失败同样保留 | 4 秒 toast 消失后没有任何入口 |

本节与第 9 节现有 P0/P1 任务表的关系是：第 6 节定义任务中心的交互和状态合同，第 9 节保留页面导航、编辑器和批处理页面职责；同一功能由任务协议/运行控制 owner 先完成身份和状态，再由导航/renderer owner 接入真实 UI。线框只作为方案，生产 UI、Electron 窄屏和多窗口行为必须单独验收。

## 7. 设计目标与当前实现边界

线框里的“当前稿/版本标识待版本服务”、输入摘要、问题定位、问题生命周期、任务详情步骤、候选采用、安全重试均是目标交互，不是本仓库当前已经持久化或可调用的 API。当前代码已能支持的基础是：Markdown 草稿保存/恢复与冲突选择、最近审核结果展示、队列/流水线状态、失败计数与日志、项目/集上下文。以下能力必须先补相应服务或数据合同，再进入 UI：

- **版本与输入快照**：需要版本/引用合同和持久化任务快照；P0 不得只改 renderer 就声称已有 `v3`、`v2` 或可复现快照。
- **问题定位与生命周期**：需要审核问题稳定 code、对象版本、段落锚点和处理记录；当前审核反馈可展示，但“点击定位正文”“新出现/仍存在/复发”是后续目标。
- **任务详情与安全重试**：需要持久任务/请求尝试、幂等或未知结果判断和恢复服务；当前 UI 只能展示现有队列/流水线状态、失败信息、日志和实际支持的停止/暂停动作。
- **候选/采用**：需要候选、采用记录和媒体引用；当前素材页的角色/场景提示词编辑不等于已有候选采用流程。

因此 P0 的立即交付只能是基于现有数据的身份过滤、错误上下文和恢复通知文案；P1/P2 的版本、定位、任务恢复、安全重试与采用流程必须在依赖完成后分别验收，不能把目标线框当作当前功能清单。

## 8. 统一组件、文案和可达性规范

### 8.1 共用组件边界

| 组件                   | 责任                                 | 不负责                    |
| ---------------------- | ------------------------------------ | ------------------------- |
| `ProjectContextHeader` | 项目、入口、当前集、版本、返回       | 不显示或修改任务内部 ID   |
| `EpisodeStageNav`      | 当前集阶段和可达性                   | 不自行决定审核门禁        |
| `NextActionCard`       | 一个主动作、原因、阻塞入口           | 不复制完整流程图          |
| `StatusBadge`          | 统一状态词、图标/文字、可读说明      | 不用颜色单独表达状态      |
| `ReviewIssuePanel`     | 问题定位、反馈、处理状态             | 不把“已处理”自动改成 PASS |
| `TaskStatusCard`       | 项目/集/阶段身份、状态、控制         | 不以日志代替状态机        |
| `RecoveryNotice`       | 恢复、冲突、失败和选择               | 不自动覆盖正文            |
| `PreflightSummary`     | 执行前显示输入、阻塞、跳过、费用未知 | 不实际执行模型调用        |

优先抽共用组件和 view-model，再调整页面；不新建第二套总控或第二套状态机。状态数据仍由现有 stores/主进程合同提供，UI 不自行授予审核或采用资格。

### 8.2 状态词和反馈

统一使用：`未开始`、`缺少输入`、`草稿未保存`、`待审核`、`审核未通过`、`已通过`、`已采用`、`需要更新`、`执行中`、`暂停处理中`、`已暂停`、`停止处理中`、`已中断`、`结果未知`、`失败`、`已完成`。作品状态（产物/审核/采用）与任务状态（运行/暂停/失败）分两行显示。

成功/警告/失败/加载分别使用页面内 `status/alert` 和 toast：关键失败必须持久可见；加载不清空旧的有效快照；空状态给出原因和下一动作；禁用按钮旁边写原因；没有“请求成功”就不能显示已完成。费用和能力未知显示“未知”，不显示零或虚假百分比。

### 8.3 键盘、焦点和窄屏

- 所有图标按钮有可读 `aria-label` 或可见文字；焦点环不可隐藏，Tab 顺序遵循页面阅读顺序。
- 可展开审核项、矩阵横向滚动区、弹窗关闭和恢复选择均支持键盘；弹窗打开时焦点进入弹窗，关闭后回到触发按钮，Escape 关闭非破坏性弹窗。
- 不以颜色/emoji 作为唯一状态信息；状态徽标同时显示文字，严重度使用文字和图标。
- 宽屏：项目页两层信息（建议 + 矩阵）；编辑页来源/正文/问题三栏，最小正文宽度优先。
- 窄屏：正文优先、来源和问题抽屉化；底部固定主动作不遮挡输入；矩阵改卡片/阶段横滑，禁止页面级横溢；批量列表分页或虚拟化。

| 继续后台任务   | 侧栏流水线或批量执行；项目矩阵可查看运行任务                           | 项目总览顶部任务卡 → 任务中心详情；始终显示项目/集/阶段，返回来源       |
| 批量运行       | 批量页选模式/集数后启动，日志和失败区分开                              | 批量预检 → 明列执行/跳过/阻塞 → 确认 → 任务中心；仍只运行 1 个          |
| 恢复草稿       | 编辑器恢复通知处理本地草稿/冲突                                        | 同一恢复通知置于正文上方，主线按钮在恢复选择完成前禁用                  |
| 生成图片/视频  | 设置可记录图片/视频配置，但图片/视频生产链尚未提供                     | 继续隐藏生产动作；待 P2 验收后从资产/镜头上下文进入候选流程             |

## 11. 真实界面走查与验收指标

以下不是本次静态审计已完成的事实，需在隔离 Electron/DOM 工具和人工走查完成：

1. 1024px 最小窗口、窄屏断点下项目矩阵、编辑器三栏、批处理无页面级横溢；抽屉可键盘打开/关闭。
2. 两个隔离项目交替加载，矩阵、审核、素材、任务和集选择不串；后台任务项目与当前浏览项目同时显示正确。
3. 首次小说、剧情、剧本各走一遍：从创建到第一项可执行工作不超过 3 个页面跳转；主动作每页 1 个，重复“前往流程页”不超过 1 处。
4. 审核不通过、读取失败、生成失败、结果未知、停止处理中、草稿冲突、可恢复中断逐一验证；每种状态都有持久原因、可达下一动作，失败不只出现在 toast/日志。
5. 批量预检可核实列出执行/跳过/阻塞，离页重返不丢任务；全局并发仍为 1。
6. 图片/视频配置页不出现未接通的生产承诺；文本模型连接/真实生成费用警示仍清楚。
7. 键盘 Tab/Enter/Space/Escape、焦点回归、屏幕阅读器名称、非颜色状态信息可核实；弹窗不困住焦点，正文编辑优先。

不设虚构的“提升百分比”。实施前后只记录可复核指标：主动作数量、重复入口数量、完成主线所需页面跳转/步骤、失败可见性、跨项目串状态用例、窄屏横溢结果、并发数。

## 12. 离线文档检查入口

本文件的检查不依赖模型、Electron、生产 API 或真实数据。仓库根目录执行：

本文件提供一个从仓库根执行的离线入口。`ROOT` 默认是当前仓库根，也可显式覆盖；隔离 worktree 缺少两份主工作区设计文档时，用 `DOC_SOURCE_ROOT` 指向主工作区的 `feicai-studio` 目录。发布文档不写死任何机器路径：

```bash
cat >/tmp/feicai-ui-ux-check.py <<'PY'
from pathlib import Path
import os, re, subprocess
root = Path(os.environ['ROOT']).resolve()
docs = root / 'feicai-studio' / 'docs'
s = (docs / 'ui-ux-optimization-plan.md').read_text()
assert s.startswith('# FEICAI Studio')
assert all(x in s for x in ('P0', 'P1', 'P2', '代码确定', '待真实界面验证'))
fallback_root = os.environ.get('DOC_SOURCE_ROOT')
if fallback_root:
    fallback = Path(fallback_root).resolve() / 'docs'
else:
    common_git = Path(subprocess.check_output(
        ['git', '-C', str(root), 'rev-parse', '--path-format=absolute', '--git-common-dir'],
        text=True,
    ).strip())
    fallback = common_git.parent / 'feicai-studio' / 'docs'
for target in re.findall(r'\]\(([^)#]+)(?:#[^)]+)?\)', s):
    if target.startswith(('http://', 'https://')):
        continue
    local = (docs / target).resolve()
    if local.exists():
        continue
    if Path(target).name in {'foundation-capabilities-design.md', 'production-workbench-media-plan.md'}:
        fallback_file = fallback / Path(target).name
        assert fallback_file.exists(), fallback_file
    else:
        raise SystemExit(f'missing local reference: {target}')
print('run_checks: document structure and references OK')
PY
cat >/tmp/feicai-ui-ux-check.mk <<'MAKE'
.PHONY: run_checks
ROOT ?= $(CURDIR)
run_checks:
	ROOT="$(ROOT)" python3 /tmp/feicai-ui-ux-check.py
	git -C "$(ROOT)" diff --check -- feicai-studio/docs/ui-ux-optimization-plan.md
MAKE
# 从仓库根执行；worktree 缺少的两份设计文档会自动从 git common dir 的主工作区读取
make -f /tmp/feicai-ui-ux-check.mk run_checks
```

将命令中的 `DOC_SOURCE_ROOT` 替换为主工作区 `feicai-studio` 目录后，从仓库根运行；也可直接 `make -f /tmp/feicai-ui-ux-check.mk run_checks DOC_SOURCE_ROOT=/实际路径/feicai-studio`。上述检查只验证文档结构、链接（含明确 fallback）和 diff 空白，不宣称是格式化检查，也不替代产品实现的 lint、typecheck、测试、Electron 冒烟或真实模型验收。
