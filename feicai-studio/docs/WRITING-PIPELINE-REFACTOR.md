# FEICAI Studio 桌面端编剧管线整体规划与重构方案

> 适用范围：`feicai-studio` 桌面端小说改编编剧管线
> 关注对象：产品、设计、前端、主进程、状态管理、内容运营
> 设计视角：以“编剧/策划/项目负责人”的连续工作流为中心，而不是以当前页面拆分为中心

---

## 1. 目标

本方案要解决的不是单页样式问题，而是桌面端编剧管线整体使用体验的结构性问题：

- 用户现在必须在 `Novel / Breakdown / AdaptScript / ScriptEditor / Review / Batch` 之间频繁跳转。
- 同一个任务在不同页面里以不同术语和状态存在，用户需要自己拼上下文。
- “创作、质检、修订、批量执行、交付”缺少一个统一的主工作台。
- 系统更像一组工具页，而不是一条完整、可掌控、可恢复的编剧生产线。

本次重构目标：

1. 把“编剧管线”从零散页面重构为一套连续、可追踪、可回退的用户旅程。
2. 以“用户当前要完成什么”组织模块，而不是以“底层引擎做了什么”组织模块。
3. 让桌面端形成明确的写作阶段主界面，并和制作阶段形成清晰交接。
4. 在不推翻当前能力的前提下，逐步收敛现有页面和 store，降低未来维护成本。

从用户视角的核心问题：

### 2.1 信息架构碎片化

- 小说导入、剧情拆解、改编规划、剧本生成、剧本编辑、审核、批量执行分别是独立页面。
- 用户必须记住“下一步该去哪个页面”，系统没有明确告诉他当前所处阶段和推荐动作。
- “写作阶段”缺少一个统一首页。

### 2.2 同一对象被多处管理

- 剧本既在 `AdaptScriptPage` 管生成，又在 `ScriptEditorPage` 管编辑。
- 审核记录在 `ReviewPage` 看，但失败后的干预入口在 `BreakdownPage / AdaptScriptPage`。
- 批量执行页承担了写作批次任务，但在导航上和制作批量任务处于同一认知层级。

### 2.3 状态表达不统一

- `adaptState`、`waterLevel`、`episode.status`、`reviewFailedData`、`lastStageReport` 各自表达不同维度，但页面没有统一翻译成用户可理解的“下一步”。
- 当前状态对用户来说是系统内部状态，不是业务状态。

### 2.4 长任务与异常恢复体验不足

- 运行中、暂停、等待用户干预、修订后重试、批次完成后闭环摘要，这些能力都存在，但分散在不同区域。
- 用户很难回答三个关键问题：
  - 现在卡在哪里？
  - 我应该处理哪一集？
  - 修完之后怎样继续？

### 2.5 从编剧到制作的交接不明确

- 写作阶段完成后，进入制作阶段是 Sidebar 上的一个按钮行为，不是一个可确认、可校验、可交付的流程。
- 用户缺少“我已经具备进入制作阶段的条件”的确认界面。

## 3. 目标用户与典型工作流

### 3.1 主要用户角色

1. 编剧/改编策划
   关注剧情拆解、分集节奏、剧本生成与修订。

2. 项目负责人/制片
   关注进度、水位、阻塞项、批量推进效率、阶段切换。

3. 审校/内容质检
   关注失败集、审核问题、修改意见闭环。

### 3.2 用户真正要完成的事

不是“打开某个页面”，而是：

1. 把原始小说转化为可用的改编输入。
2. 先得到全局改编计划，再逐步推进到分集剧本。
3. 找到当前最值得处理的一集，而不是自己扫描所有数据。
4. 快速看见失败原因、给出干预、恢复流水线。
5. 在准备充分时，把写作成果打包交接到制作阶段。

## 4. 重构后的产品结构

建议把“编剧管线”重构为一个写作阶段工作台 `Writing Workspace`，并在此之下拆成 6 个清晰模块。

### 4.1 顶层信息架构

保留现有“仪表盘 / 任务中心 / 项目”，但项目内导航重组为：

1. 编剧总控台
2. 小说源稿
3. 改编规划
4. 分集剧本
5. 质检修订
6. 交付切换
7. 制作管线

其中 `1-6` 属于写作阶段，`7` 属于制作阶段。

### 4.2 模块映射关系

现有页面到未来模块的映射：

- `NovelPage` → 小说源稿
- `BreakdownPage` → 改编规划
- `AdaptScriptPage + ScriptEditorPage` → 分集剧本
- `ReviewPage + reviewFailedData 干预入口` → 质检修订
- `BatchPage` 的写作批次能力 → 编剧总控台中的批量任务抽屉
- “进入制作阶段”按钮 → 交付切换

这意味着未来不是简单新增页面，而是合并页面职责。

## 5. 目标用户旅程

### 5.1 阶段 A：准备输入

用户进入项目后，首先看到“编剧总控台”。

系统第一屏给出项目准备度：

- 小说是否已导入
- 章节总数是否可用
- 改编规划是否已生成
- 可用剧情点是否充足
- 已生成剧本数 / 待质检数 / 失败数
- 是否满足进入制作阶段条件

如果尚未开始，页面主 CTA 不是“去某某页面”，而是：

- `导入小说`
- `初始化改编项目`
- `生成改编规划`

### 5.2 阶段 B：形成改编计划

用户进入“改编规划”模块后，应该在同一页完成两件事：

1. 看整体规划
2. 看剧情拆解水位

目标不是把“剧情点列表”和“规划 markdown”分两个心智系统，而是统一成：

- 左侧：规划视图
- 右侧：剧情库存 / 批次 / 水位 / 自动建议

系统应回答：

- 当前拆解到第几章
- 剧情库存是否足够支持下一轮剧本创作
- 哪些卷/集段仍缺规划
- 下一步推荐“继续拆解”还是“开始创作剧本”

### 5.3 阶段 C：分集创作

“分集剧本”应成为写作阶段的主战场。

这里需要把现在的 `AdaptScriptPage` 和 `ScriptEditorPage` 合并成一个双层工作区：

- 集数面板
- 当前集工作区

当前集工作区包含：

1. 剧本正文编辑器
2. 本集元信息
3. 上一轮审核反馈
4. AI 创作 / 重写 / 修订入口
5. 运行日志
6. 版本历史

用户不应再在“先生成，再跳编辑器编辑，再去审核页看失败”之间来回跳。

### 5.4 阶段 D：质检与修订

“质检修订”模块是编剧阶段的异常处理中心。

它应当聚焦三类内容：

1. 待处理失败集
2. 最近审核问题
3. 修订闭环状态

用户在这里要完成的是：

- 快速定位失败集
- 看懂失败原因
- 输入修订指令
- 重新提交
- 确认问题已关闭

这不应只是“审核记录列表”，而应是“待办问题工作台”。

### 5.5 阶段 E：批量推进

当前 `BatchPage` 应从一个独立主页面，收敛为写作阶段的“批量任务抽屉 / 批量排程中心”。

用户使用批量执行时的核心诉求是：

- 快速选集
- 快速套模板
- 快速看进度
- 快速处理异常

因此更合理的形态是：

- 在编剧总控台和分集剧本中都可打开“批量任务抽屉”
- 作为上下文动作存在，而不是单独承担导航层级

### 5.6 阶段 F：交付与切换制作

“交付切换”模块必须明确回答：

- 哪些集剧本已达制作就绪
- 哪些集仍缺审核/缺修订
- 当前项目进入制作阶段是否安全
- 进入制作后会带走哪些产物

交接应该是一套 checklist，而不是一个直接点击的按钮。

## 7. 新的用户状态模型

当前系统主要暴露内部状态。重构后需要增加用户可理解的业务状态层。

### 7.1 项目级状态

- 未开始
- 输入已准备
- 规划中
- 创作中
- 质检处理中
- 待交付
- 已交付制作

### 7.2 集数级状态

- 未进入改编
- 已分配剧情点
- 待生成剧本
- 生成中
- 待审核
- 待修订
- 可交付
- 已交付制作

### 7.3 问题级状态

- 新发现
- 待处理
- 已提交修订
- 已验证关闭
- 已忽略

这些状态应是 UI 主表达层；底层 `adaptState / reviewFailedData / lastStageReport` 继续存在，但不直接暴露给用户。

## 8. 关键交互原则

### 8.1 所有长任务必须有统一的任务反馈层

无论是拆解、创作、批量执行还是修订，都应统一使用：

- 顶部状态横幅
- 页面内当前任务卡
- 全局任务中心链接

### 8.2 所有失败都必须可恢复

用户看到失败时，必须能直接执行：

- 看原因
- 给意见
- 重试
- 回退版本

而不是只看到日志。

### 8.3 所有模块都要明确“下一步”

每个页面顶部都应该有一个推荐动作区域，例如：

- 当前剧情库存不足，建议继续拆解 2 批
- 当前有 3 集待修订，建议先进入质检修订
- 当前已满足交付条件，可进入制作阶段

### 8.4 编辑与生成不分家

用户不区分“AI 生成页面”和“手工编辑页面”；他只关心“这一集能不能写好”。

## 9. 状态与架构重构建议

当前 `useAdaptStore` 同时承担：

- 项目初始化
- 拆解与创作任务启动
- 日志与流式输出
- 审核失败干预
- 规划管理
- 用户笔记

这已经超出单一 store 的合理边界。

建议拆分为：

### 9.1 `writingWorkspaceStore`

负责项目级写作阶段概览：

- 当前项目写作准备度
- 推荐动作
- 当前活跃任务摘要
- 全局写作指标

### 9.2 `writingFlowStore`

负责长任务状态：

- 当前运行状态
- 日志
- 流式输出
- 暂停 / 恢复 / 停止
- 最近阶段报告

### 9.3 `writingPlanStore`

负责：

- 剧情拆解数据
- 水位
- 改编规划
- 用户笔记

### 9.4 `scriptWorkspaceStore`

负责：

- 集数列表
- 当前集剧本内容
- 版本
- 编辑状态
- 修订状态

### 9.5 `writingReviewStore`

负责：

- 审核结果列表
- 待修订问题
- 问题状态
- 修订闭环

### 9.6 `writingBatchStore`

负责：

- 批量创作任务
- 模板
- 调度计划
- 闭环摘要

这样可以避免一个 store 横跨所有页面，导致页面重置、事件监听和依赖收敛越来越困难。

不要再只显示“进行中/已完成”，那对管理密集型工作不够。

## 11. 与现有实现的落地映射

### 第一阶段：不改引擎，只改信息架构

目标：

- 新增“编剧总控台”
- 合并现有导航结构
- 保留现有 IPC 和 store 能力

做法：

- 先新增 `WritingWorkspacePage`
- 使用现有 `useAdaptStore + useProjectStore` 聚合数据
- Sidebar 改为写作阶段导航组

### 第二阶段：合并剧本页面

目标：

- 合并 `AdaptScriptPage` 和 `ScriptEditorPage`

做法：

- 把现有 `AdaptScriptPage` 升级为主工作台
- 把 Monaco 编辑器嵌入进去
- `ScriptEditorPage` 保留一段过渡时间后下线

### 第三阶段：重做质检修订

目标：

- 把 `ReviewPage` 从历史记录页改为问题处理页

做法：

- 优先接入 `reviewFailedData`
- 新增“待处理失败集”视图
- 审核历史作为次级 tab

### 第四阶段：BatchPage 降级为任务抽屉

目标：

- 不再让批量执行承担一级心智入口

做法：

- 在编剧总控台和分集剧本页接入批量任务抽屉
- `BatchPage` 过渡为内部容器页或任务中心子视图

### 第五阶段：交付与阶段切换产品化

目标：

- 把“进入制作阶段”升级为交付流程

做法：

- 增加 handoff checklist
- 增加交付摘要文件
- 增加阶段切换确认

## 12. 设计规范建议

### 12.1 编剧阶段页面统一框架

每页统一为：

1. 页头
2. 当前状态条
3. 主内容区
4. 右侧辅助信息区
5. 底部日志/活动区

### 12.2 核心视觉对象统一

统一 5 类组件：

- 状态徽标
- 水位卡片
- 集数卡片
- 问题卡片
- 长任务横幅

### 12.3 文案统一

内部术语改为用户术语：

- `adapt_idle` 不直接出现，显示为 `未开始`
- `breakdown_done` 显示为 `拆解完成`
- `awaitingUser` 显示为 `等待处理`
- `reviewFailedData` 显示为 `待修订问题`

## 13. 成功标准

重构完成后，用户应该可以在 10 秒内回答：

1. 当前项目写作推进到哪一步了？
2. 当前最需要处理的是哪一集/哪一类问题？
3. 下一步系统建议我做什么？
4. 我现在是否能进入制作阶段？

如果用户仍然需要记住多个页面名并自己拼接上下文，则这次重构仍然失败。

---

## 14. 结论

当前桌面端“编剧管线”的主要问题不是能力不足，而是能力分散。

现有实现已经具备：

- 小说导入
- 剧情拆解
- 改编规划
- 剧本创作
- 质检与修订
- 批量任务
- 阶段切换

真正需要重构的是：

- 用户旅程
- 信息架构
- 页面职责边界
- 状态表达
- 从写作到制作的交付机制

建议以“编剧总控台 + 6 个清晰模块 + 逐步合并现有页面”的路线推进，而不是再继续在现有独立页面上堆功能。
