# FEICAI Studio 桌面端整体重构方案

> 面向对象：产品、设计、前端、主进程、状态管理
> 范围：`feicai-studio` 项目级信息架构、左侧导航、双管线用户流程、页面职责收敛
> 目标：把“写作引擎 + 制作引擎”收敛成一条普通用户能走通的项目工作流

---

## 1. 这次要解决什么

当前桌面端不是单页复杂，而是整体结构复杂：

- 左侧菜单同时按“阶段”和“工具”组织，用户不知道下一步该去哪。
- 编剧管线和制作管线在产品层是两条路，在代码层又有多套旧入口并存。
- 同一个对象在多个页面重复管理，尤其是剧本、审核、批量任务。
- 系统把内部状态直接暴露给用户，普通用户需要自己理解引擎状态机。

这次重构的目标不是再加一层页面，而是做三件事：

1. 把两条管线重组为一条统一的项目工作流。
2. 把左侧菜单压缩成少量高频、易懂、低歧义的入口。
3. 把“批量、审核、提示词、日志”从主导航项降级为上下文能力。

---

## 2. 现状问题诊断

结合现有实现，问题主要集中在以下四类。

### 2.1 导航层级过深，且新旧结构并存

当前 Sidebar 已经引入“编剧管线 / 制作管线”分组，但项目内仍然暴露了大量平级入口：

- `编剧总控台`
- `小说源稿`
- `改编规划`
- `分集剧本`
- `质检修订`
- `交付切换`
- `流水线`
- `批量执行`
- `素材库`
- `提示词`
- `分集剧本`
- `审核报告`

这里的问题不是数量多本身，而是这些入口混合了三种维度：

- 阶段入口
- 工具入口
- 结果入口

用户会自然产生三个困惑：

1. “分集剧本”为什么在写作和制作里都出现？
2. “审核”到底是写作审核，还是制作审核？
3. “批量执行”是项目阶段，还是只是一个运行方式？

### 2.2 同一对象被重复管理

当前重复最明显的是剧本：

- `AdaptScriptPage` 管“生成 + 编辑 + 修订 + 集数工作区”
- `ScriptEditorPage` 也管“按集编辑剧本”

审核也存在类似问题：

- `ReviewPage` 同时承接写作质检和制作审核记录
- 失败后的处理入口却散落在 `BreakdownPage`、`AdaptScriptPage`、`WritingHandoffPage`

批量任务同样重复：

- `BatchPage` 负责项目内批量运行
- `TaskCenterPage` 又负责全局任务查看与调度记录

这意味着用户不是在“完成一个任务”，而是在“猜哪个页面对这件事负责”。

### 2.3 产品模型仍然暴露内部引擎模型

当前前端核心状态分散在三套 store：

- `projectStore`：项目与集数
- `adaptStore`：小说拆解、规划、剧本生成、质检等待
- `pipelineStore`：导演、美术、分镜执行

这在工程上没有问题，但在产品层直接映射为页面和状态，就会产生认知负担。

普通用户真正关心的是：

- 有没有输入
- 能不能继续写
- 哪一集卡住了
- 能不能送制作
- 什么时候能导出

而不是：

- `breakdown_executing`
- `adapt_awaiting_user`
- `director_reviewing`
- `art_done`

### 2.4 旧路由仍在，导致信息架构没有真正收口

虽然已经新增 `/writing/*` 路由，但旧入口仍在共存：

- `/project/:id/novel`
- `/project/:id/breakdown`
- `/project/:id/adapt-script`
- `/project/:id/script`
- `/project/:id/review`
- `/project/:id/batch`

这说明产品层已经想走“新工作流”，但路由层和页面职责还没有彻底清理，结果就是：

- 用户看到的是新旧混杂
- 研发维护的是重复入口
- 后续设计无法建立稳定认知

## 3. 重构原则

### 3.1 对用户只展示一条主流程

内部可以保留两个引擎，但用户只应看到一条连续流程：

`内容准备 -> 剧本创作 -> 画面制作 -> 交付导出`

### 3.2 一个核心对象只保留一个主页面

- 小说输入只在“内容准备”里管理
- 剧本只在“剧本创作”里管理
- 制作执行只在“画面制作”里管理
- 导出和切阶段只在“交付导出”里管理

### 3.3 主导航只放稳定入口

不把“批量执行、审核记录、提示词、日志”放到主导航。

这些能力应该作为：

- 页面内 tab
- 右侧抽屉
- 底部面板
- 二级操作

而不是左侧一级菜单。

### 3.4 面向普通用户命名，避免术语泄漏

要减少“流水线、拆解水位、阶段状态机”这类工程语言，主文案改成任务语言：

- 内容准备
- 剧本创作
- 画面制作
- 问题处理
- 交付导出

### 3.5 状态显示分两层

- 第一层：用户业务状态
- 第二层：高级细节和日志

也就是默认先回答“能不能继续”，再回答“底层现在在哪个 stage”。

---

## 4. 新的整体产品结构

建议把项目内结构重组为 5 个稳定模块。

## 4.1 左侧菜单新结构

全局区：

1. 项目
2. 任务中心
3. 设置

当前项目区：

1. 工作台
2. 内容准备
3. 剧本创作
4. 画面制作
5. 交付导出

说明：

- `项目` 对应 Dashboard，不再让首页只承担“项目列表 + 零散卡片”。
- `工作台` 是当前项目的唯一总入口，负责下一步建议、进度、异常、快捷动作。
- `内容准备` 合并小说源稿与改编规划。
- `剧本创作` 合并剧本生成、编辑、修订、写作质检。
- `画面制作` 合并流水线、素材、提示词、制作审核、制作批量执行。
- `交付导出` 合并交付切换与导出。

---

## 5. 两条管线如何重组为一条流程

### 5.1 用户视角的新流程

#### 阶段 A：内容准备

用户完成：

- 导入小说或其他源内容
- 核对项目基本信息
- 生成改编规划
- 补充剧情库存

系统产出：

- 可追溯的内容源
- 可用的规划与剧情库存

#### 阶段 B：剧本创作

用户完成：

- 选择集数
- 生成剧本
- 编辑剧本
- 根据质检反馈修订剧本
- 批量推进多集创作

系统产出：

- 可交付的分集剧本

#### 阶段 C：画面制作

用户完成：

- 选择待制作集数
- 启动导演 / 美术 / 分镜生产
- 查看素材和提示词
- 处理制作审核问题
- 批量推进多集制作

系统产出：

- 素材、设计结果、分镜提示词、制作审核记录

#### 阶段 D：交付导出

用户完成：

- 检查哪些集已经具备交付条件
- 决定局部交付还是整体交付
- 导出项目产物

系统产出：

- 项目交付包
- 导出文件
- 阶段完成标记

### 5.2 内部仍然保留两套引擎

产品层统一，不等于引擎层合并。

仍建议保留：

- `adaptStore` / `adapt-state-machine` 负责内容准备与剧本生成
- `pipelineStore` / `pipeline-runtime-manager` 负责画面制作

但前端页面不再围绕 store 拆页，而是增加一层“工作台视图模型”来做聚合。

## 6. 新页面职责设计

### 6.1 工作台

目标：成为项目唯一默认入口。

页面内容：

- 项目阶段进度
- 当前推荐动作
- 风险与阻塞项
- 最近活动
- 各阶段摘要
- 快捷入口

工作台只回答四个问题：

1. 现在做到哪了
2. 卡在哪里
3. 下一步是什么
4. 我点哪里

当前 `WritingWorkspacePage` 已经有这个方向，但仍只覆盖编剧阶段。建议升级为项目级工作台。

### 6.2 内容准备

合并现有：

- `NovelPage`
- `BreakdownPage`

页面结构建议：

- 顶部：内容准备概览
- 左 tab：源稿
- 右 tab：改编规划
- 右侧边栏：库存状态、推荐动作、用户笔记

去掉“为了看规划再跳一个页面”的成本。

### 6.3 剧本创作

合并现有：

- `AdaptScriptPage`
- `ScriptEditorPage`
- 写作阶段的 `ReviewPage`
- 写作批量任务相关能力

页面结构建议：

- 左侧：集数导航与队列状态
- 中间：剧本编辑区
- 右侧：AI 操作、审核反馈、版本与日志
- 抽屉：批量任务

这里必须成为唯一剧本页面，避免“双剧本页面”继续存在。

### 6.4 画面制作

合并现有：

- `PipelinePage`
- `AssetPage`
- `PromptPage`
- 制作阶段 `ReviewPage`
- `BatchPage`

页面结构建议：

- 顶部：选择当前集数、当前制作状态
- 主 tab：
  - 制作流程
  - 素材资产
  - 提示词
  - 审核问题
- 右侧：运行日志 / 最近批量任务

这样“素材、提示词、审核”都成为制作场景下的上下文信息，而不是左侧一级菜单。

### 6.5 交付导出

合并现有：

- `WritingHandoffPage`
- 导出入口

页面结构建议：

- 项目交付准备度
- 分集交付状态表
- 导出配置
- 历史导出记录

“进入制作阶段”不再表现为单独按钮，而是“交付动作”之一。

## 7. 左侧菜单的精简方案

### 7.1 推荐的最终菜单

```text
项目
任务中心

当前项目
- 工作台
- 内容准备
- 剧本创作
- 画面制作
- 交付导出

设置
```

### 7.2 需要从左侧菜单移除的项

- 小说源稿
- 改编规划
- 质检修订
- 流水线
- 批量执行
- 素材库
- 提示词
- 审核报告
- 导出

原因不是这些功能不重要，而是它们不适合作为一级导航存在。

### 7.3 新的“问题处理”入口方式

`质检修订` 不建议继续单独放左侧。

更合理的方式：

- 在工作台显示“待处理问题数”
- 在剧本创作页和画面制作页显示“问题”tab
- 在任务中心保留全局问题与运行记录

也就是“问题跟着场景走”，而不是“问题单独成站”。

## 8. 状态模型重做建议

### 8.1 面向用户的统一业务状态

建议在前端增加项目级派生状态：

- `draft`：待准备
- `ready_for_writing`：可开始写作
- `writing_in_progress`：写作中
- `writing_blocked`：写作阻塞
- `ready_for_production`：可送制作
- `production_in_progress`：制作中
- `production_blocked`：制作阻塞
- `ready_to_export`：可导出
- `completed`：已完成

### 8.2 内部状态继续保留，但降到二级展示

例如：

- 业务状态显示：`写作阻塞`
- 次级说明显示：`EP012 剧本质检未通过，等待修订`
- 高级日志再显示：`script_reviewing -> adapt_awaiting_user`

这样既保留调试能力，也不会把状态机直接扔给普通用户。

## 9. 对现有代码的直接改造建议

### 9.1 路由层

建议收敛成以下规范路由：

- `/`
- `/tasks`
- `/settings`
- `/project/:id/workspace`
- `/project/:id/source`
- `/project/:id/script`
- `/project/:id/production`
- `/project/:id/delivery`

旧路由全部保留一版重定向，不再作为真实页面继续维护：

- `/project/:id/writing`
- `/project/:id/writing/source`
- `/project/:id/writing/plan`
- `/project/:id/writing/scripts`
- `/project/:id/writing/qa`
- `/project/:id/writing/handoff`
- `/project/:id/novel`
- `/project/:id/breakdown`
- `/project/:id/adapt-script`
- `/project/:id/script`
- `/project/:id/pipeline`
- `/project/:id/assets`
- `/project/:id/prompts`
- `/project/:id/review`
- `/project/:id/batch`

### 9.2 页面层

建议保留并升级：

- `WritingWorkspacePage` -> `ProjectWorkspacePage`
- `WritingHandoffPage` -> `DeliveryPage`

建议合并重构：

- `NovelPage + BreakdownPage` -> `SourcePage`
- `AdaptScriptPage + ScriptEditorPage + writing Review` -> `ScriptWorkspacePage`
- `PipelinePage + AssetPage + PromptPage + production Review + BatchPage` -> `ProductionPage`

### 9.3 状态层

建议新增一个只做前端聚合的 selector/store：

- `workspaceStore` 或 `useProjectWorkspace`

它不替代现有 store，只做三件事：

1. 聚合 `projectStore + adaptStore + pipelineStore`
2. 产出项目级业务状态
3. 给工作台和左侧菜单提供统一摘要数据

### 9.4 组件层

建议新增三类共用组件：

- `StageSummaryCard`
- `IssuePanel`
- `ContextActionDrawer`

让批量任务、审核、日志、提示词这些能力都能以下钻形式复用，而不是继续长成整页。

## 10. 分阶段落地顺序

### Phase 1：先收口，不大拆

目标：先把信息架构稳定下来。

- 调整左侧菜单
- 统一 header 标题
- 新建规范路由
- 旧路由改为重定向
- 工作台升级为项目级入口

### Phase 2：先统一剧本工作区

目标：解决最明显的重复。

- 合并 `AdaptScriptPage` 和 `ScriptEditorPage`
- 把写作审核反馈嵌回剧本工作区
- 批量写作改成抽屉

### Phase 3：再统一制作工作区

目标：减少制作侧导航噪音。

- 把 `PipelinePage / AssetPage / PromptPage / ReviewPage / BatchPage` 收成一个制作页
- 按 tab 和抽屉组织信息

### Phase 4：最后统一交付与导出

目标：形成完整闭环。

- 交付检查与导出合并
- 项目 phase 切换并入交付动作
- 形成完整项目收尾体验

---

## 11. 这套方案带来的变化

### 对用户

- 不再需要理解两条管线和一堆工具页。
- 不再需要猜“这件事到底在哪一页做”。
- 能更快看到当前项目下一步。

### 对设计

- 页面职责更稳定，交互边界更清晰。
- 可以围绕“任务完成”设计，而不是围绕“功能清单”设计。

### 对研发

- 路由数量减少，页面重复减少。
- 状态映射更清晰，后续加能力不容易继续膨胀菜单。
- 可以保留底层引擎，不需要推翻主进程架构。

---

## 12. 结论

`feicai-studio` 当前最需要的不是再补几个页面，而是把产品模型收紧。

真正应该让用户看到的是：

`工作台 -> 内容准备 -> 剧本创作 -> 画面制作 -> 交付导出`

而不是：

`写作页面 + 制作页面 + 工具页面 + 旧页面 + 新页面`

如果按这个结构重做，桌面端会从“懂系统的人才能用的工具集合”，变成“普通用户能理解的项目工作台”。
